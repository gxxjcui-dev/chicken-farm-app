## ✅ 已完成的核心修改

### 1. 外键关联策略（全部改为Batch.id）

| 表名 | 修改前 | 修改后 | 状态 |
|------|--------|--------|------|
| **EnvironmentReading** | 关联DailyRecord.batchId | 关联Batch.id + onDelete: Restrict | ✅ |
| **EquipmentOperationLog** | 关联DailyRecord.batchId | 关联Batch.id + onDelete: Restrict | ✅ |
| **ManagerDecisionLog** | 关联DailyRecord.batchId | 关联Batch.id + onDelete: Restrict | ✅ |
| **HealthMedicationEvent** | 关联DailyRecord.batchId | 关联Batch.id + onDelete: Restrict | ✅ |
| **KnowledgeConflictLog** | 关联DailyRecord.batchId | 关联ManagerDecisionLog.id + Batch.id | ✅ |

**核心原则：**
- ✅ 所有批次级事件直接关联Batch.id
- ✅ 不关联DailyRecord（DailyRecord是派生聚合表）
- ✅ 所有外键使用onDelete: Restrict（保护历史数据）

### 2. KnowledgeConflictLog关联调整

**修改前：**
```prisma
model KnowledgeConflictLog {
  batchId BigInt @map("batch_id")
  dailyRecord DailyRecord? @relation(fields: [batchId], references: [batchId])
}
```

**修改后：**
```prisma
model KnowledgeConflictLog {
  managerDecisionId BigInt @map("manager_decision_id")
  batchId Int @map("batch_id") // 保留用于查询
  recordDate DateTime @db.Date @map("record_date") // 保留用于查询
  
  managerDecision ManagerDecisionLog @relation(fields: [managerDecisionId], references: [id], onDelete: Restrict)
  batch Batch @relation(fields: [batchId], references: [id], onDelete: Restrict)
}
```

**理由：**
- 冲突日志必须追溯到具体决策（哪次决策产生的冲突）
- 保留batchId和recordDate用于查询
- 符合"冲突由厂长主动勾选产生"的业务逻辑

---

### 3. DailyRecord唯一约束

**新增：**
```prisma
@@unique([batchId, recordDate])
```

**作用：**
- 确保同一批次同一天只能有一条日报
- 防止重复日报导致的死淘双倍计算

---

### 4. MigrationMapping字段规则

**修改前：**
```prisma
legacySubrecordKey String @default("default") @map("legacy_subrecord_key")
```

**修改后：**
```prisma
legacySubrecordKey String @map("legacy_subrecord_key")
```

**业务层规则：**
- 一对一迁移：明确传入 `'default'`
- 一对多迁移：必须传入稳定、可重复计算的子记录Key（如 `'env_01'`, `'med_02'`）
- 不允许NULL
- 不依赖数据库默认值自动填充

---

### 5. 辅助索引补充

**MigrationLog新增索引：**

**EnvironmentReading新增索引：**

### 6. ManagerDecisionLog新增字段

**新增字段：**

**作用：**


```
  ├─ EnvironmentReading (环境读数) [关联Batch.id]

```

## 🔒 数据安全保障

### 外键删除策略

所有外键统一使用 `onDelete: Restrict`：

```prisma
batch Batch @relation(fields: [batchId], references: [id], onDelete: Restrict)
```

**作用：**
- ✅ 禁止删除有关联数据的批次
- ✅ 保护历史生产数据完整性
- ✅ 防止误删除导致的数据丢失

## 📝 DDL变更清单

### 需要执行的SQL变更

**1. DailyRecord表：**
```sql
-- 添加唯一约束
ALTER TABLE daily_records ADD CONSTRAINT uk_daily_records_batch_date UNIQUE (batch_id, record_date);
```

**2. EnvironmentReading表：**
```sql

ALTER TABLE environment_readings DROP CONSTRAINT IF EXISTS environment_readings_batch_id_fkey;
ALTER TABLE environment_readings ADD CONSTRAINT environment_readings_batch_id_fkey 
  FOREIGN KEY (batch_id) REFERENCES batches(id) ON DELETE RESTRICT;

CREATE INDEX idx_environment_readings_batch_layer_time ON environment_readings(batch_id, cage_layer, read_time);
```

**3. EquipmentOperationLog表：**
```sql
-- 修改外键
ALTER TABLE equipment_operation_logs DROP CONSTRAINT IF EXISTS equipment_operation_logs_batch_id_fkey;
ALTER TABLE equipment_operation_logs ADD CONSTRAINT equipment_operation_logs_batch_id_fkey 
  FOREIGN KEY (batch_id) REFERENCES batches(id) ON DELETE RESTRICT;
```

**4. ManagerDecisionLog表：**

## ⚠️ 注意事项

### 数据迁移前检查

在执行DDL变更前，请确认：

1. ✅ 已备份当前数据库
2. ✅ 已确认现有表结构和数据
3. ✅ 已确认没有违反新约束的数据（如重复的batch_id + record_date）

### 迁移顺序

建议按以下顺序执行：

1. **先执行不依赖外键的变更**（添加字段、添加索引）
2. **再执行外键修改**（需要先删除旧外键，再添加新外键）
3. **最后执行唯一约束**（需要确保没有重复数据）

### 回滚方案

如果迁移失败，可以使用以下回滚SQL：

```sql
-- 回滚DailyRecord唯一约束
ALTER TABLE daily_records DROP CONSTRAINT IF EXISTS uk_daily_records_batch_date;

-- 回滚外键（改为ON DELETE CASCADE或其他策略）
-- ... 根据需要编写
```
